# Kodigo Module Authoring Guide

**Audience:** an LLM session (or a person) turning lecture material, usually a PDF deck, into a complete, importable study module for the Kodigo site.
**Contract:** follow this document exactly. The site validates every module against it on import and rejects anything that doesn't conform.
**Schema version covered:** `schemaVersion: 1`

---

## 0. For the human: how to use this guide

Start a new chat (ideally inside the "bdcc midterms reviewer" Claude Project, where this guide already lives) and attach:
1. the lecture PDF,
2. this file (`MODULE_AUTHORING_GUIDE.md`),
3. `WIDGETS.md` (generated by the site: Admin → "Download widget reference"; it's always up to date),
4. *(recommended)* a reference module as a bundle: Admin → `fim` → "Export as bundle text".

Then paste:

```text
Build a Kodigo study module from the attached lecture, following MODULE_AUTHORING_GUIDE.md exactly.

Module id: <kebab-case-id>
Title: <full title>
Short title (≤ 12 chars): <tab label>
Course: BDCC — Sessions <x–y>, dated <yyyy-mm-dd>
Prerequisite modules: <ids, or none>
Anything my professor emphasized / exam format notes: <optional>

Work in the order the guide prescribes (SOURCE_NOTES → datasets → logic.js → examples → verify → the rest).
Output a single bundle in the bundle text format. Do not abbreviate any file.
```

Import it via **Admin → Import → Paste LLM output**. If validation fails, click **"Copy fix request for LLM"**, paste that into the same chat, and re-import the corrected files.

*With repo access (Claude Code):* write the files to `modules/<id>/`, run `pnpm kodigo validate modules/<id>` until it's clean, then `pnpm kodigo pack modules/<id>`.

## 1. Your task (for the LLM)

Produce **one module**: a folder of files that teaches one topic three ways and supplies a bank of auto-generated practice questions.

| Tab | Purpose | File |
|---|---|---|
| **Intuition** | guided, animated, interactive scenes in the style of a 3Blue1Brown video; the math is built up *inside* the visuals | `intuition.yaml` |
| **Math & Code** | derivations side by side with Python; each formula term is linked to the code lines that compute it | `math-code.yaml` |
| **Application** | a notebook-style case study that ties it all together, plus how it's done at scale | `application.yaml` |
| **Quiz** (global) | parameterized question templates; numbers change every time | `quiz.yaml` |

Behind them sit `logic.js` (all computation), `datasets/` (all data), `examples.yaml` (the lecture's own numbers, used as tests), `glossary.yaml`, `manifest.yaml`, and `SOURCE_NOTES.md` (your extraction of the source).

**You never write UI code.** You compose widgets from a fixed catalog (§9) and supply pure functions. The site renders and animates.

---

## 2. Mandatory workflow

Do these in order. Don't skip steps 1–4; they are what makes the module *correct*.

1. **Extract** → write `SOURCE_NOTES.md` (§5.2): every concept in lecture order, every formula verbatim, **every worked example with exact numbers and slide refs**, conventions, ambiguities, errata.
2. **Model the data** → `datasets/*.yaml` (§5.3), using the lecture's own examples first.
3. **Implement** → `logic.js` (§5.4): one pure function per formula or algorithm, with traces for anything step-by-step.
4. **Verify** → `examples.yaml` (§5.5): encode every worked example from step 1 as fn + input → expected output. **Mentally execute (or actually run, if you have a tool) every example against your `logic.js`.** If a number doesn't reproduce, your *convention* is wrong. Revisit `SOURCE_NOTES.md` → *Conventions*. Only call it a slide error (errata) if you can show that the slide contradicts itself or basic arithmetic.
5. **Glossary** → `glossary.yaml` (§5.6).
6. **Math & Code** → `math-code.yaml` (§5.8): one section per formula or algorithm.
7. **Intuition** → `intuition.yaml` (§5.7): scenes that build each idea from a concrete question.
8. **Application** → `application.yaml` (§5.9).
9. **Quiz** → `quiz.yaml` (§5.10), plus generator functions added to `logic.js`.
10. **Manifest** → `manifest.yaml` (§5.1): skills must cover everything referenced.
11. **Self-check** → go through the checklist in §12 and fix issues before outputting.

### 3.2 Bundle text format (for chat output)

Wrap the whole answer like this. Every file must be **complete**: no `...`, no "same as above", no omitted sections.

```text
<<<BUNDLE fim@1.0.0>>>
<<<FILE manifest.yaml>>>
schemaVersion: 1
id: fim
...complete file content...
<<<END FILE>>>
<<<FILE datasets/grocery5.yaml>>>
```

- Don't put the bundle inside a Markdown code fence, and don't add commentary between files.
- If you run out of room, **end after a complete `<<<END FILE>>>`** with a line `<<<CONTINUE>>>`. When the user says "continue", resume with the next `<<<FILE …>>>`. The importer concatenates pastes.

## 4. Shared syntax (used in every file)

### 4.1 IDs
- Pattern `^[a-z0-9]+(-[a-z0-9]+)*$` (kebab-case), unique **within their kind** in the module.
- IDs are **permanent**: progress is keyed on them. When revising a module, never rename an existing ID.
- Item names inside datasets (e.g. `bread`, `kape-3in1`) follow the same pattern. Put pretty names in the dataset's `labels`.
- Matrix row and column labels: letters, digits, `_` or `-` only (no spaces or commas), e.g. `HP1`, `A`, `u1`.

### 4.2 Markdown (`Markdown` fields)
CommonMark + GFM tables. Inline math `$…$`, display math `$$…$$` (KaTeX). Interpolation `{=…}` is allowed (§4.4). Keep prose short (word limits in §11).

### 4.3 TeX (`Tex` fields) and math anchors
- KaTeX-compatible LaTeX only (no `\usepackage`, no `align` environments; use `\begin{aligned}…\end{aligned}` inside display math).
- **Anchor a term** so the site can link it to code and to trace steps: `\anchor{name}{content}`, for example
  `\frac{\anchor{sup-ab}{\text{Sup}(A \cup B)}}{\anchor{sup-a}{\text{Sup}(A)}}`.
  Anchor names use `[a-z0-9_-]+` (**lowercase only**: `solve-v`, not `solveV`; a camelCase name is silently not an anchor and
  the validator reports it as missing), and the same name may appear in several steps. The same rule applies to code anchors (§4.6)
  and to the `code`/`math` names in trace steps.

### 4.4 Interpolation `{=path|format}`
Inserts a live value from the current **scope** (§4.5) into Markdown or TeX.

| Format | Result |
|---|---|
| *(none)* | numbers: rounded to 2 dp, trailing zeros stripped (`0.5`, `2.5`, `0.67`); strings as-is; arrays as `a, b, c` |
| `\|0`…`\|6` | round to N dp, strip trailing zeros |
| `\|2f` (any N) | fixed N dp (keeps zeros: `0.50`) |
| `\|frac` | exact-looking fraction if the denominator ≤ 12 (`10/3`, `-7/3`), else 2 dp |
| `\|pct` | percentage, 0 dp (`40%`); `\|pct1` for 1 dp |
| `\|int` | integer |
| `\|set` | itemset: in TeX → `\{\text{bread}, \text{milk}\}`, in Markdown → `{bread, milk}` (uses dataset labels) |
| `\|list` | `a, b, c` |
| `\|text` | TeX only: wraps a string in `\text{}` |

Paths use dots: `{=c.conf|2}`, `{=freq.count}`, `{=pair.0}`.

### 4.5 Scope and references `@path`
Every scene, section, case study and quiz instance has a **flat scope** made of:
1. **datasets** listed in `data:` (by id; the value is the dataset payload, see §5.3),
2. **state** keys (`state:`; widgets can change them),
3. **derived** values (`derive:` outputs, recomputed whenever state changes),
4. in quizzes: **generator vars**.

Names must not collide across these four sources. **State keys, `derive.out` names and generator vars are identifiers** (`^[A-Za-z_][A-Za-z0-9_]*$`, camelCase recommended, e.g. `minsup`, `freq`, `supAB`), because `when` expressions and dot paths use them. Dataset IDs used in `when` expressions must not contain hyphens (`grocery5`, not `grocery-5`); for datasets that's recommended anyway.

A YAML value that is a string starting with `@` is a **reference**: `'@grocery5'`, `'@freq.supportMap'`, `'@c.conf'`. References must be the *entire* value (use `{=…}` for text). **Always quote references in YAML** (`'@x'`), because `@` is reserved.

### 4.6 Code anchors
In `code.source`, mark lines that implement an anchored math term. The markers are removed before display.

```python
def confidence(A, B, transactions):
    # @a sup-ab
    sup_ab = abs_support(A | B, transactions)
    # @end
    sup_a = abs_support(A, transactions)      # @a:sup-a
    return sup_ab / sup_a                      # @a:ratio
```
- Block form: a line containing only `# @a name` starts the block, and `# @end` closes the most recent open block. Blocks may nest.
- Single-line form: a trailing `# @a:name`.
- Comment prefixes: `#` (python, bash, yaml, r), `//` (js, ts, java, c, scala), `--` (sql).
- **Every anchor used in a section's TeX must exist in its code, and vice versa** (validated).

### 4.7 Selectors, tones, commands
Widgets are addressed with **selectors** (strings, per widget, listed in §9), such as `row:3`, `set:bread,milk`, `cell:A,HP1`, `term:sup-ab`, `anchor:sup-ab`.
**Tones:** `accent` (focus), `good` (kept, frequent, correct), `bad` (pruned, wrong), `warn`, `muted`.
**Common commands** (all widgets): `highlight {sel, tone?}`, `pulse {sel}`, `annotate {sel, text}`, `clear {sel?}`.

**Persistence rule:** `highlight` and `pulse` are *transient*: they last for the current beat or trace step only. Every other command (`strike`, `prune`, `fill`, `project`, `annotate`, `center`, …) *persists* until the scene or player resets. The engine rebuilds state by replaying persistent commands, which is what makes back and scrub work, so commands must be deterministic.

### 4.8 YAML rules (avoid parser errors)
- 2-space indentation, no tabs, and no anchors or aliases (`&`, `*`).
- Use a **block scalar `|`** for any Markdown or TeX longer than a few words, and for anything containing `\`.
- Use **single quotes** for short strings containing `: # { } [ ] @ & * ! | > % ,` or starting with a special character. Inside single quotes, write `''` for a literal `'`.
- **Never use double quotes for TeX** (backslash escapes break it).
- Numbers that must stay strings (dates, `3-4`) go in quotes.

## 5. File specifications

The TypeScript types below are **normative**: the site's validator implements them. `?` means optional.

```ts
type Id = string;                 // kebab-case, §4.1
type Markdown = string;           // §4.2 (+ {=} §4.4)
type Tex = string;                // §4.3 (+ {=} §4.4)
type Ref = string;                // '@path', §4.5
type Value = string | number | boolean | null | Value[] | { [k: string]: Value };
type Prop = Value | Ref;
type Tone = 'accent' | 'good' | 'bad' | 'warn' | 'muted';
type LessonRef = { tab: 'intuition' | 'math-code' | 'application'; id: Id }; // scene id | section id | cell id
```

### 5.1 `manifest.yaml`

```ts
interface Manifest {
  schemaVersion: 1;
  id: Id;                          // permanent
  version: string;                 // semver; bump when you revise
  title: string;
  shortTitle: string;              // ≤ 12 chars (tab label)
  summary: Markdown;               // ≤ 50 words
  course?: string;                 // e.g. BDCC
  order?: number;                  // tab order (10, 20, 30…)
  color?: string;                  // hex accent, e.g. '#0ea5e9'
  icon?: string;                   // a lucide icon name, e.g. shopping-basket, users, grid-3x3
  sources: { title: string; file?: string; sessions?: string; date?: string }[];
  prerequisites?: Id[];            // other module ids
  skills: { id: Id; label: string; description?: string }[];   // 6–12 skills
  requires: { widgets: string[] }; // every widget name used anywhere in the module
  authoring?: { generatedBy?: string; generatedAt?: string; notes?: string };
}
```

### 5.2 `SOURCE_NOTES.md` (required; not rendered to learners, kept for audit)

```markdown
# Source notes — <title>
## Source
- File: … | Sessions: … | Date: … | Pages: …
## Concept inventory (lecture order)
1. <concept> — slides a–b — one-line summary
## Formulas (verbatim, as TeX)
- <name>: `<tex>` — slide n
## Worked examples (exact numbers)
- <what> — slide n — inputs … → outputs …   (→ example id)
## Conventions & ambiguities
- <decision> — evidence (e.g., "reproduces 0.89, 0.94 in slide 9 table only if computed over co-rated items")
## Errata
- slide n: says X, should be Y, because …
## Beyond the slides
- <what you added> — why (mark these `beyondSlides: true` / Callout kind `beyond`)
## Skill map
- <skill-id>: concepts …
```

### 5.3 `datasets/<id>.yaml`

```ts
type Dataset =
  | { id: Id; kind: 'transactions'; title?: string; source?: string; description?: Markdown;
      labels?: Record<string, string>;                       // item id → display label
      transactions: { id: string | number; items: string[] }[] }
  | { id: Id; kind: 'matrix'; title?: string; source?: string; description?: Markdown;
      rows: string[]; cols: string[]; values: (number | null)[][] }   // null = missing
  | { id: Id; kind: 'table'; title?: string; source?: string; description?: Markdown;
      columns: string[]; rows: Value[][] }
  | { id: Id; kind: 'list'; title?: string; source?: string; items: Value[] }
  | { id: Id; kind: 'json'; title?: string; source?: string; value: Value };
```

**Payload seen through `@id`:** transactions → the `transactions` array; matrix → `{rows, cols, values}`; table → `{columns, rows}`; list → `items`; json → `value`. Labels from all datasets are merged into a module-wide label map that widgets and `|set` use automatically.

Rules: the lecture's examples come first and are **verbatim**. Application datasets should be realistic and small (≤ 40 rows; matrices ≤ 10×12). Local flavor (Philippine context) is welcome.

### 5.4 `logic.js` (all computation lives here)

A **plain ES module with no imports and no build step**. It runs inside a Web Worker.

```js
export default function register(sdk) {
  // helpers you need, destructured from sdk
  const { isSubset, sortSet, key, powerset, round } = sdk;

  function support({ transactions, itemset }) { /* … */ return { abs, rel, hits }; }
  function confidence({ transactions, A, B }) { /* … */ return { supAB, supA, conf, trace }; }

  function confidenceQ({ rng, difficulty, fns, sdk }) { /* … */ return { vars, misconceptions }; }

  return {
    fns: { support, confidence /* , … */ },
    generators: { confidenceQ /* , … */ },
  };
}
```

**Rules for `fns`:**
1. **Pure and deterministic.** No `Math.random`, `Date`, `fetch`, DOM, timers, or state shared between calls.
2. **One object argument in, one plain object out.** Never return a bare number: FunctionPlot fns return `{ y }`. Output must be JSON-serializable (no `Set`/`Map`/`undefined`; use `null`).
3. **Canonical outputs:** itemsets are arrays sorted by a stated order (use `sdk.sortSet`); lists of results are sorted deterministically.
4. **Full precision.** Never round inside fns (display formatting and example tolerances handle it). *Exception:* if the lecture explicitly rounds intermediates and that changes a result, add an option such as `roundIntermediate: 2` and document it in SOURCE_NOTES.
5. **Fast:** < 50 ms per call at module data sizes; traces ≤ 400 steps.
6. Anything that is a step-by-step process in the lecture returns a **`trace`** (below).
7. fns can call each other directly (they're in the same closure).

**Trace format** (drives `StepPlayer`, math↔code step-through, and animations):

```ts
interface TraceStep {
  label: Markdown;                         // ≤ 20 words; {=…} can use this step's vars
  code?: string;                           // code anchor to light up (role 'code')
  math?: string;                           // TeX anchor to light up (role 'formula')
  vars?: Record<string, Value>;            // shown as debugger-style badges; available to label
  ops?: { role: string; cmd: string; args?: Value }[];  // widget commands addressed by ROLE
  patch?: Record<string, Value>;           // state patch applied at this step (undone on reset/seek back)
}
```
Roles are abstract names (`table`, `lattice`, `matrix`, `sims`, `code`, `formula`…) that the scene maps to concrete widget IDs in `StepPlayer.props.roles`. Document the roles each trace fn uses in a comment above it.

**Rules for `generators`** (quiz):

```ts
type Generator = (ctx: { rng: Rng; difficulty: 1 | 2 | 3; fns: Fns; sdk: Sdk }) => {
  vars: Record<string, Value>;                   // merged into the question's scope
  options?: Markdown[];                          // for mcq/multi (overrides static options)
  answer?: number | number[];                    // option index(es) for mcq/multi
  misconceptions?: { var?: string; value?: number; feedback: Markdown }[];
};
```
- Compute answers **by calling `fns`**, so quiz answers and lessons can never disagree.
- Produce **hand-computable** problems: small tables (≤ 8 transactions, ≤ 6 items, matrices ≤ 5×6), integer ratings, results with small denominators. Difficulty 1 = one step on a tiny table; 3 = a multi-step computation on a lecture-sized table.
- **Reject ambiguous draws** and redraw (loop with `rng`): ties at a top-k cutoff, zero denominators, answers equal to a misconception value, degenerate cases (everything frequent, all similarities 0).
- Put every value the prompt, visuals, explanation and steps need into `vars`.

**`sdk` reference:**

| Function | Purpose |
|---|---|
| `rng` (in ctx) → `.float()`, `.int(lo, hi)` (inclusive), `.pick(arr)`, `.sample(arr, k)`, `.shuffle(arr)`, `.bool(p)` | seeded PRNG (only in generators) |
| `round(x, d = 2)`, `fmt(x, spec)`, `frac(x, maxDen = 12)` → string, `approx(a, b, tol = 1e-9)` | numbers |
| `sum(a)`, `mean(a)`, `dot(a, b)`, `norm(a)`, `cosine(a, b)` (0 if either norm is 0) | vectors |
| `zeros(m, n)`, `transpose(M)`, `matmul(A, B)`, `solve(A, b)` (small dense systems), `rowMeans(M)` (ignores `null`), `observed(M)` → `[[i, j], …]` | matrices (`null` = missing) |
| `eigSym(S)` → `{values, vectors}` (Jacobi), `pinvSym(S, tol?)` (pseudo-inverse of a symmetric matrix), `lstsq(A, b)` (**minimum-norm** least squares, like `numpy.linalg.lstsq`; use it when a system can be rank-deficient, e.g. ALS from a symmetric start) | linear algebra |
| `combinations(arr, k)`, `powerset(arr, {min = 1, max})`, `sortSet(set, order?)`, `key(set, order?)` → `'a,b'`, `isSubset(a, b)`, `union`, `intersect`, `difference` | sets (arrays) |
| `log2(x)`, `range(n)`, `assert(cond, msg)` | misc |

`key(set, order)` is the canonical itemset key used by `ItemsetLattice` (`support` maps and `set:` selectors).

### 5.5 `examples.yaml` (the lecture's numbers, used as tests)

```ts
interface ExamplesFile { examples: Example[] }
interface Example {
  id: Id;
  source: string;            // 'Sessions 3–4, slide 43'
  page?: number;             // PDF page number (handouts often hold several slides per page)
  fn: string;                // a key of fns
  in: Record<string, Prop>;  // refs resolve to datasets
  expect: Record<string, Value>;  // dot-paths into the fn result → expected value
  tol?: number;              // abs tolerance for numbers; default 0.005
  note?: Markdown;
}
```
- Include **every numeric result the lecture shows** where feasible (≥ 1 per math-code section; usually 8–25 per module).
- **Tolerance follows the slide's displayed precision:** 2 dp → `0.01`; 1 dp → `0.05` (slides often round intermediates, so allow half a unit plus slack).
- Arrays compare element-wise in order (so fns must return canonical order).
- Import is **blocked** if any example fails.

### 5.6 `glossary.yaml`

```ts
interface GlossaryFile { terms: Term[] }
interface Term {
  id: Id; term: string; aka?: string[];
  short: string;               // ≤ 25 words, standalone definition (used in auto-quizzes; don't include the term itself)
  long?: Markdown; formula?: Tex; related?: Id[]; lessonRef?: LessonRef; skills?: Id[];
}
```
Every technical term the lecture uses gets an entry (typically 10–25). Definitions in the same module must be distinguishable, because they become distractors for each other.

### 5.7 `intuition.yaml` (guided scenes)

```ts
interface IntuitionFile { scenes: Scene[] }
interface Scene {
  id: Id; title: string;
  goal: string;                     // one learner-facing sentence: the question this scene answers
  skills?: Id[];
  data?: Id[];                      // dataset ids brought into scope
  state?: Record<string, Value>;
  derive?: Derive[];
  stage: StageWidget[];             // the persistent stage for the whole scene
  beats: Beat[];                    // shown one at a time
  takeaway: Markdown;               // ≤ 25 words
}
interface Derive { fn: string; in: Record<string, Prop>; out: string }   // result stored in scope as `out`
interface StageWidget {
  id: Id; widget: string;           // catalog name, §9
  props?: Record<string, Prop>;
  bind?: Record<string, string>;    // widget output name → state key (two-way)
  region?: 'main' | 'side' | 'top' | 'bottom';   // default 'main'
  hidden?: boolean;                 // start hidden; reveal with beat.show
}
interface Beat {
  id?: Id;
  say: Markdown;                    // narration, ≤ 60 words
  set?: Record<string, Prop>;       // state changes → widgets animate to them
  show?: Id[]; hide?: Id[];
  do?: { target: Id; cmd: string; args?: Value }[];
  gate?: Gate;
}
type Gate =
  | { type: 'continue'; label?: string }
  | { type: 'predict'; question: Markdown; options?: Markdown[];            // omit options → numeric input
      answer: number | { value: number; tol?: number }; explain: Markdown }
  | { type: 'when'; prompt: Markdown; when: string;                         // expression over scope
      hint?: Markdown; skippable?: boolean }                                // skippable defaults true
  | { type: 'event'; prompt: Markdown; target: Id; event: string; hint?: Markdown; skippable?: boolean };
```
`when` expressions use Kodigo's own small, sandboxed expression parser (no `eval`): `==, !=, <, <=, >, >=, and, or, not, + - * / %`, parentheses, numbers, `'strings'`, `true`/`false`/`null`, dot paths (`freq.count`, `pair.0`), plus the functions `len(x)`, `has(arr, v)`, `abs(x)`, `round(x, d)`, `min(…)`, `max(…)`. Example: `'freq.count == 1 and minsup >= 4'`.

`@refs` inside a beat's `do[].args` are resolved against the scene scope when the beat runs, so `{ target: m, cmd: fill, args: { cell: 'u3,i1', value: '@f.p31' } }` works.

**How animation happens:** change state with `set` (or let the learner change it through a bound widget) and the widgets tween to the new values. Use `do` commands for emphasis and for structural moves (`prune`, `project`, `center`, `focus`…), and a `StepPlayer` to play an algorithm's trace across several widgets. **Keep the same widgets on stage across beats** and change what they show; don't swap widgets. That visual continuity is what makes it feel like one smooth video.

### 5.8 `math-code.yaml` (side-by-side derivations)

```ts
interface MathCodeFile { sections: Section[] }
interface Section {
  id: Id; title: string; skills: Id[];
  summary: Markdown;                  // ≤ 60 words
  keyFormula?: Tex;                   // goes to the cheat sheet; no {=}
  data?: Id[]; state?: Record<string, Value>; derive?: Derive[];   // the live example
  steps: { tex: Tex; say: Markdown }[];     // derivation, ≥ 2 steps; last step may substitute live numbers via {=}
  code: { lang?: string; title?: string; source: string };          // default lang python; ≤ 30 lines
  extraCode?: { lang?: string; title: string; source: string }[];   // e.g. vectorized version
  links: { anchor: string; label: string; say?: Markdown }[];       // one per anchor used; legend order
  trace?: { fn: string; in: Record<string, Prop> };                 // enables "Step through"
  examples?: Id[];                    // lecture checks shown in this section
  pitfalls?: Markdown[];
  examTip?: Markdown;
  errata?: Markdown[];
  beyondSlides?: boolean;             // true if this section goes beyond the source
}
```
**Code rules:** idiomatic, readable, from-scratch Python; the standard library, plus `numpy` only where matrices make it clearer. Mirror the math's names (`mu_u`, `sim`, `s_vj`, `sup_ab`) and the **lecture's conventions exactly** (same ordering, same tie-breaks, same neighbor rules). The Python must compute the same results as the matching `logic.js` fn. Define small helpers once (e.g. `abs_support`) and reuse them by name in later sections; a helper used but not shown in a section is assumed from an earlier section.

For a trace in math-code, the roles `code` and `formula` map automatically to the section's code pane and derivation pane. The trace fn's `code` and `math` anchors must exist there.

### 5.9 `application.yaml`

```ts
interface ApplicationFile {
  intro: Markdown;                                   // why this matters in practice, ≤ 80 words
  case: {
    id: Id; title: string; story: Markdown;          // a realistic scenario

```
The case study should **use every major idea from the lecture in one pipeline**: raw data, then computation with live parameters, then interpretation, then a decision. `atScale` shows the production or big-data version (for BDCC, typically PySpark MLlib, or pandas/mlxtend, SQL, or MapReduce as appropriate) with notes on complexity, parallelism and data size. Mark anything not in the lecture with a `Callout` of kind `beyond`.

- A question instance is `(template id, seed)`. Everything must render from the generator's `vars` plus static fields.
- **Code-fill matching** ignores all whitespace and treats `'` and `"` as equal, so keep `accept` lists minimal but include genuine alternatives (`len(transactions)` and `len(D)` if both are valid in context).
- **Misconceptions** are *specific wrong methods*, computed by the generator (`var`) or fixed (`value`), with feedback that names the mistake. The engine ignores any that coincide with the correct answer.
- Glossary questions are auto-generated. **Don't** write plain "define term X" templates; write `term`-tagged templates only for richer conceptual distinctions.

**`logic.js`** (excerpt)
```js
export default function register(sdk) {
  const { isSubset, sortSet, key, powerset } = sdk;
  const ORDER = ['bread', 'butter', 'cheese', 'eggs', 'milk', 'yogurt']; // lecture uses alphabetical order

  function support({ transactions, itemset }) {
    const set = sortSet(itemset);
    const hits = transactions.filter(t => isSubset(set, t.items)).map(t => t.id);
    return { abs: hits.length, rel: hits.length / transactions.length, hits };
  }

  // roles: table (TransactionTable), code, formula
  function confidence({ transactions, A, B }) {
    const both = support({ transactions, itemset: [...A, ...B] });
    const ante = support({ transactions, itemset: A });
    const conf = ante.abs === 0 ? null : both.abs / ante.abs;
    return {
      supAB: both.abs, supA: ante.abs, conf,
      trace: [
        { label: 'Baskets containing A ∪ B: {=supAB}', math: 'sup-ab', code: 'sup-ab',
          vars: { supAB: both.abs },
          ops: [{ role: 'table', cmd: 'highlight', args: { sel: both.hits.map(id => `row:${id}`), tone: 'good' } }] },
        { label: 'Baskets containing A: {=supA}', math: 'sup-a', code: 'sup-a',
          vars: { supA: ante.abs },
          ops: [{ role: 'table', cmd: 'highlight', args: { sel: ante.hits.map(id => `row:${id}`), tone: 'accent' } }] },
        { label: 'Confidence = {=supAB} / {=supA} = {=conf|2}', math: 'ratio', code: 'ratio',
          vars: { supAB: both.abs, supA: ante.abs, conf } },
      ],
    };
  }

  function frequentItemsets({ transactions, minsup }) {
    const items = sortSet([...new Set(transactions.flatMap(t => t.items))], ORDER);
    const supportMap = {};
    const frequent = [];
    for (const s of powerset(items)) {
      const abs = support({ transactions, itemset: s }).abs;
      supportMap[key(s, ORDER)] = abs;
      if (abs >= minsup) frequent.push({ itemset: s, abs });
    }
    return { supportMap, frequent, count: frequent.length };
  }

  // Quiz: confidence on a fresh small database
  function confidenceQ({ rng, difficulty, fns }) {
    const pool = ['bread', 'butter', 'cheese', 'eggs', 'milk', 'yogurt'];
    for (;;) {
      const n = difficulty === 1 ? 5 : 7;
      const transactions = Array.from({ length: n }, (_, i) => ({
        id: i + 1, items: sortSet(rng.sample(pool, rng.int(2, 4)), pool),
      }));
      const [a, b] = rng.sample(pool, 2);
      const r = fns.confidence({ transactions, A: [a], B: [b] });
      const supB = fns.support({ transactions, itemset: [b] }).abs;
      if (r.supA < 2 || r.supAB < 1 || r.supAB === r.supA || supB === 0) continue; // avoid trivial or undefined cases
      if (r.supA === n || supB === r.supA) continue;                                  // a misconception would equal the answer
      return {
        vars: { transactions, A: [a], B: [b], supAB: r.supAB, supA: r.supA, conf: r.conf,
                wrongDivN: r.supAB / n, wrongReversed: r.supAB / supB },
        misconceptions: [
          { var: 'wrongDivN', feedback: 'You divided by the number of transactions. Confidence divides by **Sup(A)**, the baskets that contain the antecedent.' },
          { var: 'wrongReversed', feedback: 'That is conf(B → A). Direction matters: divide by the support of the **antecedent**.' },
        ],
      };
    }
  }

  return { fns: { support, confidence, frequentItemsets }, generators: { confidenceQ } };
}
```

## 7. Pedagogy rules

### 7.1 Intuition (the 3Blue1Brown feel)
- **Open with a question or puzzle** (`goal`), not a definition. Concrete before abstract: show the lecture's own data first, then vary it.
- **One idea per beat**, ≤ 60 words. Narration explains the *idea*, never the UI ("drag the slider" is fine; "this widget displays…" is not).
- **Math grows out of the picture.** Put a `Formula` on stage and reveal it with `step` as the visual explains each part; highlight a term (`term:<anchor>`) at the moment the corresponding thing happens.
- **Predict before reveal:** at least one `predict` gate per scene. At least half of the scenes need an interactive gate (`when` or `event`) where the learner *does* something (drag, reorder, tune a parameter).
- **Continuity:** same widgets across beats; animate by changing state. Colors carry meaning consistently (`good` kept/frequent, `bad` pruned/wrong, `accent` current focus).
- **Surface insights and traps:** each module should have 1–3 "aha" scenes built on a surprising fact from the data (the FIM deck has *the milk trap*: conf = 1 but lift = 1).
- End every scene with a one-sentence `takeaway`.
- **Size:** 6–10 scenes, 4–10 beats each; every skill appears in at least one scene. Order scenes to follow the lecture.

### 7.2 Math & Code
- One section per formula or algorithm in the source, in lecture order. Derivations proceed in small steps: definition, then symbolic form, then live numbers.
- **Anchor every term that matters** in both panes (≥ 2 anchors per non-trivial section).
- Give the live example the lecture's numbers, and list the matching `examples`.
- Pitfalls come from real mistakes (they should mirror your quiz misconceptions). An exam tip is one practical sentence.
- Add sections that go beyond the slides only when they're genuinely useful (for example, regularization in ALS), and mark them `beyondSlides: true`.

### 7.3 Application
- Keep one coherent story from start to finish, and connect it to prior modules when relevant (`connections`).
- Include ≥ 3 `decision` cells where the learner must *interpret* results (which rule to act on, which recommender to trust, why a metric misleads).
- Always include `atScale`, `tradeoffs` and `explainBack`.

### 7.4 Quiz bank quotas (minimum per module)
- **≥ 25 templates**, **≥ 2 per skill**.
- ≥ 8 generator-driven `numeric` or `hand-calc` · ≥ 2 `hand-calc` that mirror the lecture's worked procedure step by step · ≥ 6 conceptual `mcq`/`multi` · ≥ 4 `code-fill` · ≥ 2 `order` · ≥ 2 `match`.
- Every numeric template has **≥ 2 misconceptions**. MCQ distractors should be *plausible wrong answers* (ideally computed from misconceptions), never joke options.
- Difficulty spread is roughly 40% level 1, 40% level 2, 20% level 3.

## 8. Correctness rules (what the validator and a careful reviewer check)

1. Every lecture number you cite reproduces from `logic.js` (examples pass).
2. The conventions in `SOURCE_NOTES.md` explain *why* those numbers come out that way.
3. Errata are logged, not silently "fixed". Lessons show the correct value plus a `Callout` of kind `errata`.
4. Python in `math-code` computes the same thing as the JS fn it sits next to.
5. Quiz answers come from `fns` (no hand-typed answers for generated questions).
6. Every reference resolves: widgets, fns, generators, datasets, `@refs`, `{=paths}`, anchors, `lessonRef`s, skill IDs, glossary `related`.
7. IDs are unique and kebab-case; `requires.widgets` lists exactly the widgets used.

## 13. Common mistakes to avoid

- Picking a formula variant from memory instead of the lecture's (e.g., Pearson over all items when the lecture uses co-rated items only). **The lecture's numbers decide the convention.**
- Forgetting a step the lecture leaves implicit (e.g., adding μᵤ back after a mean-centered prediction). Teach it explicitly and note it in SOURCE_NOTES.
- Generators that produce ugly decimals, ties at the k-th neighbor, or divisions by zero.
- Misconception values equal to the right answer for some seeds (redraw).
- Narration that restates the formula in words without the *why*.
- Computation embedded in YAML: all numbers come from `logic.js` or datasets.
- Renaming IDs when revising. Add new ones and retire old ones instead (removed IDs simply stop appearing).
- Double-quoted TeX in YAML (`"\frac"` breaks). Use `|` or single quotes.

## 14. Revising a module and answering fix requests

- **Fix request from the importer:** output **only the files listed**, each **complete**, in bundle format, with the same `id` and `version` unless told otherwise.
- **Content revision:** bump `version` (patch for fixes, minor for new scenes or templates), keep all existing IDs, and add a line to `authoring.notes`.
- **Splitting a module:** the new module gets a new id; the old one keeps its ids for the content that stays.
